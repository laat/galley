# galley

Local pull request staging server: a CLI mirroring `gh pr`/`gh api` for agents, a GitHub-like web UI for review, and publishing to GitHub. See README.md for the user-facing picture.

## Commands

- `pnpm test`: node:test, `test/**/*.test.ts` and `desktop/test/*.test.ts`, with Node's compile cache in `node_modules/.cache`, so that the CLI and the servers the tests start do not strip the types of the same modules again in every process. CI runs it in four shards, each on a runner of its own (`.github/workflows/test.yml`). The files in `test/e2e/` run the whole agent loop against a temp repo, a bare remote and a fake `gh`, one feature per file, each with a server of its own from `startHarness()` (`test/helpers/harness.ts`): node runs the files in parallel and the tests in a file in sequence, so the longest file sets the suite's time. A test file that starts a server or runs the CLI imports `./helpers/env.ts` first, which keeps it off the user's galley, config, `gh`, `codex`, `claude` and the network. In a reviewer agent's sandbox the end-to-end tests need the setting "Let Claude's tests listen on localhost", and the install sandbox's tests skip themselves where they can not start one: macOS does not nest sandboxes, and bwrap needs unprivileged user namespaces.
- A test that fails and then passes with nothing changed, locally or in CI, is a flake: once the rerun passes, file an issue on laat/galley for it before you move on. Give the test's name and file:line, the failing GitHub Actions run's URL or the command you ran, the assertion and its output, and what you know of the cause, saying what is a guess. Leave out staged numbers and galley's URLs, which nobody else can open. When an open issue already has that flake, comment on it with the new failure instead. Where you can not reach GitHub, as in a reviewer agent's sandbox, say in your answer that it flaked, with the same details.
- `pnpm typecheck`: `tsc --noEmit` (TypeScript 7).
- `pnpm build`: the npm package, galley-proof (its command is `galley`), in `dist/` (`scripts/build.ts`), which `npm pack ./dist` packs. `.github/workflows/release.yml` stages it on npm when a GitHub Release is published, for the user to approve with 2FA; `.claude/skills/release/SKILL.md` says how to cut one.
- `pnpm dev`: server on :24823 with `--watch`. Use `GALLEY_HOME=<tmp> node bin/galley.ts serve --port 0` for a throwaway instance (it prints the URL of the port it got), and stage against a scratch repository or a mirror, not the one you work in.
- `GALLEY_NO_AUTOSTART=1 node bin/galley.ts …`: the CLI from a worktree. Without the variable, a call made while the server is away starts one from the branch's code.

## Conventions

- No build step in development: Node 24 strips types. Only erasable syntax (no enums, no parameter properties, no namespaces), and relative imports end in `.ts`. The npm package is built, since Node strips types from no file under node_modules: it has each module as `.js` in the checkout's layout. A path to one of galley's own modules, which no import rewrites, takes the extension of the module it is in (`extname(import.meta.filename)`).
- `src/cli` never touches the database or galley's clones; it talks HTTP to the server: the API, and git's smart HTTP to send branches and fetch them back. The server never reads or writes the agent's checkout. When nothing answers at a local URL on a machine that has run a server (its database is in the data directory), `src/cli/client.ts` starts a detached `galley serve`, so agents never have to.
- API responses copy GitHub's REST shapes (snake_case); `gh --json` output copies gh's shapes (camelCase). Both live in `src/server/github.ts`. Additions beyond GitHub are named as extensions in comments.
- HTML is built with the `html` tagged template (`src/server/web/html.ts`), which escapes every interpolation unless it is `Safe`. Use `raw()` only for markup we produced (sanitized markdown, highlight.js output, octicons).
- Every state change goes through `Service` and calls `emit()`, or `emitSystem()` for one no actor made (from GitHub or git), which drives live UI updates and wakes `pr wait`.
- Live updates reach the browser through one SharedWorker (`public/live-worker.js`) shared by all tabs. Never open an EventSource or other long-lived request per tab: browsers allow six HTTP/1.1 connections per host, and the seventh tab hangs.
- Each document has one reader. README.md is for users: what they can see and do, a sentence or two per feature. Implementation details and edge cases go in code comments where they apply, agent instructions in the galley skill, which lives in the user's dotfiles (`~/.dotfiles/galley/.agents/skills/galley/SKILL.md`), not here, and API extensions in `docs/api.md`.

## Layout

- `src/server/service.ts`: domain logic: repos, pulls, revisions (push detection), reviews, comments, line placement, wait, publish.
- `src/server/events.ts`: a pull request's timeline events, written and read back typed by their type. Some decide what galley does next: whether a push signs, whether a failed push is tried again.
- `src/server/feedback.ts`: what others post on a pull request, and what of it asks something of the author; `pr wait` (`Service.wait`), `Service.turn` and `Reviewer.answered` read it here.
- `src/server/github-follow.ts`: what galley reads about a published pull request on GitHub (merge, checks, review decision, threads, conflicts) to show the reviewer; `Service.followGithub` asks GitHub on a timer. The author agent hears only of a merge or close.
- `src/server/diff.ts`: unified diff parser, `mapLine` for carrying comments across revisions.
- `src/server/git.ts`: git plumbing, cached when all inputs are full SHAs.
- `src/server/api.ts`: REST routes under `/api`.
- `src/server/git-http.ts`: git's smart HTTP at `/git/<owner>/<name>.git`, through `git http-backend`, for galley's own clones of GitHub repositories (`Service.registerGithub`; `Service.migrateRepos` moves repositories registered by path into them at start), which the CLI sends branches to (`src/cli/send.ts`); `receive-hook.ts` is the pre-receive hook its pushes go through.
- `src/server/computer.ts`: which computer a request comes from (behind `tailscale serve`, the address last in X-Forwarded-For), so that pages and the CLI hand off only to a desktop app on their own computer.
- `src/server/check.ts`: `galley serve --check`: whether the server's machine has what galley needs (gh's login and scopes, signing, Codex and Claude Code logged in, bwrap and socat on Linux), without printing what those tools say.
- `src/server/uploads.ts`: images pasted into comments, stored in the data directory by the SHA-256 of their bytes and served from `/uploads/`.
- `src/server/reviewers/reviewer.ts`: a reviewer agent: triggered by the `author-waiting` bus event, reviews in a temporary checkout (installing the dependencies first when it may run the tests) and posts a review as its bot, one attempt per head (per version of the description for a reviewer of the description: `Reviewer.subject`) within the per-pull-request limit. Each is one actor whose login follows its name (`meta.<engine>_actor_id`, or `meta.reviewer_actor_id:<name>` for a custom reviewer), and the API refuses CLI callers that claim it. What differs per tool is its `Engine` (`Reviewer.engine`, whose id is `Reviewer.engineId`): how to run it, its models, how to read its answer.
- `src/server/reviewers/head-status.ts`: where a reviewer agent stands with a pull request's head (`Reviewer.headStatus`), and what each state counts as: for whose turn it is, for handing the head to the user, for auto-publish.
- `src/server/reviewers/codex.ts`: Codex as an engine: `codex exec` in Codex's sandbox (default name `codex-review`; `--reviewer codex` finds it by its engine). The CLI calls author agents running in Codex `codex-agent`.
- `src/server/reviewers/claude.ts`: Claude as an engine: `claude -p` in Claude Code's sandbox (default name `claude-review`, since author agents in Claude Code are `claude`); its installs run in `sandbox.ts` (`sandbox-exec` on macOS, `bwrap` on Linux). The Codex and Claude reviewers' settings live in `src/server/settings.ts`.
- `src/server/reviewers/install.ts`: installing a pull request's dependencies before a review, only from a lockfile and without running anything the repository provides (no lifecycle scripts).
- `src/server/reviewers/transcript.ts`: what a reviewer agent does while it reviews, as ACP `session/update` updates that each engine reads its tool's stream into (`EngineJob.onUpdate`). Stored per run, capped, for the run's transcript page (`src/server/web/runs.ts`); the latest steps are followed in memory for the sidebar, which hears of them through `progress` events, not `change`.
- `src/server/reviewers/custom.ts`: custom reviewers: the user's own, one Markdown file each in `<configDir>/reviewers`, run by Codex's or Claude's engine. Each is a `Reviewer` whose `key` (in `review_runs.reviewer` and the API) is its name; it reviews the repositories its globs match (`Service.reviewersFor`), the code or the description (title, description and commit messages), and may approve, which never counts toward `reviewDecision`. Its settings are its file; its per-pull-request settings are JSON in `pulls.reviewer_overrides`.
- `src/server/reviewers/definition.ts`: a custom reviewer's file: front matter with its settings (`engine`, `repos`, `reviews`, `verdict`, `max_iterations`, …) and a body with its instructions. Reads, checks and writes them.
- `src/server/auto-publish.ts`: auto-publish (after GitHub's auto-merge): publishes a pull request the reviewer approved in advance once `Service.readiness` says the agents are done with it; after publishing, pushes each head the author waits with, and publishes its edits of the title and description (`Service.pushReady`, `Service.editsReady`, `Service.pushUpdate`).
- `src/server/web/`: server-rendered pages; `public/app.js` adds the interactive parts (event delegation, soft refresh that keeps drafts).
- `src/config.ts`: what the server and the CLI share: the port and URL, the data directory and `configDir()`, the `GALLEY_*` variables (`fromEnv`), who the CLI acts as (`cliActor`) and the GitHub repository a remote names (`githubSlug`).
- `desktop/`: the macOS app (Electron), a package of its own with its own lockfile, so the root's install never downloads Electron. `main.ts` has the windows (galley's origin only, no preload), the menu-bar status, the notifications and galley:// links (`src/app-link.ts`), which `galley browse`, `--web` (`src/cli/open.ts`) and pages opened in the browser (`public/app.js`) hand off to; `server.ts` attaches to the server or starts it as the CLI does; `live.ts` is the main process's one `/events` stream; `turns.ts` reads the open pull requests with their turn from the API in one request and says which became the user's turn; `menu.ts` makes the menu-bar title and menu of them; `pages.ts` says which of galley's URLs are not pages, with no header, which on macOS is the window's title bar (`public/app.css`). Its windows go back and forward with a swipe and with ⌘← and ⌘→ through `public/gestures.js`, which `public/app.js` loads in the app only. Its tests (`desktop/test/`) are in the root suite and use nothing from `desktop/node_modules`; `pnpm --dir desktop typecheck` checks `main.ts` with Electron's types. `build.ts` builds a `galley.app` that runs the checkout's `main.ts`.
- `src/cli/`: the CLI: `main.ts` starts the server for `serve` and hands the other commands to `pr.ts` (`gh pr`), `api.ts` (`gh api`), `browse.ts` and `reviewers.ts`; `client.ts` talks HTTP to the server, and registers the checkout; `send.ts` sends the author's branch to galley's clone and fetches back what galley fetched from GitHub, with git over HTTP, and keeps a remote called galley in the checkout; and `format.ts` prints pull requests, threads and conversations.
