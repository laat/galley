# API

The server speaks a subset of GitHub's REST API under `/api` (pulls, review comments, reviews,
issue comments, the timeline, commits and contents), in GitHub's shapes, so `galley api` calls
look like `gh api` calls. This page lists only what galley adds. Paths starting with `…` are
under `/api/repos/{owner}/{repo}`.

## Hosts and links

- The server takes requests addressed to `localhost`, `127.0.0.1` or `[::1]` at its port, the address it listens on, its public URL's host (`galley serve --public-url`, `GALLEY_PUBLIC_URL`), and the hosts in `--allowed-host` or `GALLEY_ALLOWED_HOSTS`; others get 403. A request other than GET or HEAD that has an `Origin` gets 403 unless it is `http://` or `https://` one of those hosts.
- Links in responses (`html_url`, `url`, a user's generated `avatar_url`) start with the public URL, by default the server's URL on its machine.

## Identity

- `X-Galley-Actor: <login>`: who the caller is; without it, the user. `X-Galley-Actor-Type: User|Bot` (default `Bot` unless the login is the user's). A reviewer agent's name is refused with 409.
- `X-Galley-Client: <where>`: where the CLI runs, such as `<hostname>:<git directory>`. `POST …/pulls` keeps it with the pull request, as `client` in the gh shapes.
- Another agent can review as a GitHub review bot does, under its own name: `GALLEY_ACTOR=reviewer galley pr review <n> --comment -b "…"`, or `POST …/pulls/{n}/reviews`. Its reviews wake the author's `pr wait` like the user's.
- Callers of type `Bot` get 403 from what is the user's to do: deleting, pinning, stop-iterating, settings, and asking for or configuring a reviewer agent.
- Publishing and turning auto-publish on or off are the user's and the pull request's author's: other callers of type `Bot`, such as an agent reviewing under its own name, get 403. Auto-publish publishes as whoever turned it on.
- Bringing back commits a rewrite on GitHub removed (`bring_back` when publishing) is the user's from galley's page only: a request with `X-Galley-Actor`, whatever its type, or without the browser's `Origin` header gets 403 for it. Like the rest of the API, this goes by headers: there is no authentication, so it keeps out the CLI and plain API calls, not a caller that sends a browser's headers on purpose.

## Pull requests

- `GET …/pulls?state=`: also `staged`, `published`, `done`, `merged` and `all`. `state` is `closed` once the pull request is done, merged on GitHub included.
- `GET /api/pulls?state=`: every repository's pull requests in one list, as `…/pulls` lists them (latest update first), each with its `repository` as `GET /api/repos` has it.
- `POST …/pulls`: `reviewers` (logins, or `{"login": "codex", "max_iterations": 3}`) turns those reviewer agents on: an engine (`codex`, `claude`), a name in settings, or a custom reviewer of the repository. `automatic_reviews: false` turns all of them off. Unknown logins come back in `ignored_reviewers`.
- `DELETE …/pulls/{n}`: delete a staged pull request.
- `POST …/pulls/{n}/publish`: push and open or update the pull request on GitHub. Body `{sign, draft, force, expected, during_review, during_conflict, auto_merge, merge_method, bring_back}`. `merge_method` defaults to the one in settings; from galley's page it must be that one or auto-publish's, any other caller may name another. For the author agent, as for auto-publish, each step (signing, the push, each `gh` call) gets 2 minutes, so a signing prompt nobody answers fails; a failed signing's error has `signing` (`why`, and `transient`: trying again later may get past it). 428 lists what the body must acknowledge in `acknowledge`; 412 when the pull request (`expected`, the page's fingerprint) or the merge method changed. A head that would bring back commits a rewrite on GitHub removed gets 409 with them in `bring_back`; with each of them (full SHAs) in the body's `bring_back`, it is pushed all the same, and the `published` event lists them in `brought_back`. Auto-publish never brings any back. The response adds `auto_merge_result`.
- `PUT|DELETE …/pulls/{n}/auto-publish`: turn auto-publish on (body `{sign, draft, force, auto_merge, merge_method}`, `merge_method` as for publishing) or off. It approves the first publish only: 422 once published. When signing fails in a way trying again may get past (a prompt nobody answered, a signing agent that is not running), it stays on and tries again after 5, 15 and 45 minutes, up to the `signingRetries` setting, whether the author still waits or not; each failure is an `auto_publish_retry` event in the timeline (`error`, `head`, `approval`, and `signing`: `why`, `failures`, `retries`, `next_at`). After that, or for any other failure, it turns off with an `auto_publish_failed` event (`error`, and `signing` when signing failed). `signing.final` marks a failure trying again can not get past, and `why` says what happened when galley can tell: a prompt the user denied or dismissed is final at once, as is ssh-agent's refusal, which it also gives when locked, when nobody touched a security key, or when it could not show its confirmation.
- `GET …/pulls/{n}/wait?timeout=<s>`: long-poll for the author. `status` is `feedback`, `agents_done`, `conflicts`, `published`, `pushed`, `push_failed`, `edited`, `edit_failed`, `closed`, `merged`, `closed_on_github` or `timeout`, with `pr` (the gh shape), `agents_done`, `conflicts`, `push`, `edit`, `left_out`, `asks_author`, `still_to_review` and `seen_at`. `conflicts` is the head when it conflicts with its base as galley works it out against the base it fetches, before and after publishing, said once per commit. `asks_author` says whether the author has anything to address once it has read what came: feedback that asks something of it (anything from anyone else but an approval without comments, or a reviewer agent's review that found nothing), a thread waiting for its answer (unresolved, with someone else's comment the latest), or a reviewer agent's findings in the head it has not answered; `still_to_review` is what the reviewer agents that still have the head to review are at. Both are null with `agents_done` and `timeout`. Once published, a wait with a head GitHub does not have pushes it, signed as the last publish was and force-pushed only with a lease on what galley pushed last; `push` says how (`source`, `head`, `before`, `force`, `signed`, `result`, `error`, `retry`, `signing`, `fetched`, `rewritten`), and is in the timeline as a `github_push` event. A push GitHub refused is `push_failed`, and is not tried again for that commit; when the branch there has commits galley does not have, galley fetches it into its remote-tracking branch for the author to rebase onto, and `fetched` says where and at what (`ref`, `sha`, and `rewritten` when the branch there no longer has the commit galley pushed last, or a tip galley fetched since, with `since`, after which the author's own commits to rebase come: the staged head galley pushed last, or the tip it rebased onto since), or why it could not (`error`); one that failed otherwise (`retry`) is tried again at the author's next wait, which hears nothing of it. A push whose signing failed has `signing`, as auto-publish's: one trying again may get past is tried again at `signing.next_at`, whether the author waits or not, up to the `signingRetries` setting, and after that, or at once for any other signing failure, it is `push_failed`. A head that has the fetched branch in it is pushed on top of it, with a lease on it (`before`). When that branch was rewritten, as galley found when it fetched it since its last push, `rewritten` says from what to what (`from`, `to`; also on the timeline's `published` event when publishing pushed so), and a head that still has commits the rewrite removed, or whose signed copies would bring them back, is refused before any push: `push_failed` with `fetched`, or a 409 when publishing. Once published, a wait also publishes the author's edits of the title and description, before any push: each that GitHub does not have and that only the author edited since it was last published. One the user edited since stays the user's to publish, also when the author edited it after the user. `edit` says what came of it, and is in the timeline as a `github_edit` event: `published`, what GitHub got (`title`, `description`); `edited_on_github`, what was left alone because GitHub's differs from what galley last published (someone edited it there); `failed`, with `error`; `read_upto`, the pull request's latest event when galley read the text it tried, after which an edit counts as one since; and the `title` and `body` it tried. With a push, `status` is the push's, and the wait answers once both are done; without one, `edited`, or `edit_failed` when something was left. A field left is not tried again with the same text, except one that failed because GitHub could not be reached or asked (`retry`): that is tried again at the author's next wait, which hears nothing of it. The `published` event has `read_upto` too. With `merged`, `left_out` is what the branch has that GitHub did not merge, or null: `commits` (`sha`, `parents`, `message`; oldest first), synced before galley heard of the merge or made after it, but none on a remote-tracking branch, such as the base's (copies a rebase made of published ones count); `head`, the branch's tip; and `deleted`, true when the branch is gone and `head` is what galley last saw of it.
- `PUT …/pulls/{n}/seen`: the author confirms it showed a wait's result: `{at, agents_done?, conflicts?}`.
- `PUT|DELETE …/pulls/{n}/pinned`: pin to the top of the front page.
- `PUT|DELETE …/pulls/{n}/stop-iterating`: stop the reviewer agents' automatic reviews, or resume them.
- `PUT …/pulls/{n}/viewed`: `{path, blob, viewed}`, a file's "Viewed" box.

Fields on a pull request: `staging_state` (`staged`, `published`, `done`), `published_url`, `published_at`, `github_state` (`open`, `merged`, `closed`; null until asked), `github_closed_at`, `github_closed_by`, `author_waiting`, `auto_publish`, `iterations_stopped`, `turn` (`whose`: `author`, `reviewer_agents`, `reviewer`, `none`, and `reasons`; a reviewer agent's reason has its `state` and `to_review`, true while it still has the head to review; `none` also while auto-publish is on and waits for nothing of the user's, with one reason of kind `auto_publish` saying what it waits for, and once published while a push whose signing failed for now waits to be tried again, with a reason of kind `unpublished` saying so; on the user's turn, a reason of kind `auto_publish` says what holds auto-publish up that no other reason does), `unpublished_changes`, `pinned_at`.

## Review comments and threads

- `PUT|DELETE …/pulls/{n}/threads/{id}/resolved`: resolve or unresolve a thread.
- `POST …/pulls/{n}/pending-comments`: add a comment to the caller's pending review, starting one.
- A comment may sit on an unchanged line of a changed file, outside the diff's hunks.
- Fields on a review comment: `priority`, `outdated`, `resolved`.
- A comment's `html_url` (and `url` in the gh shapes) is the Conversation tab at the comment, `…/pull/{n}#discussion_r{id}` or `#issuecomment-{id}`, also for a thread that is outdated or on a commit's message, which Files changed does not show. Opened, the page opens the thread or file that hides it; on a tab that does not show it, it goes on to the one that does.

## Reviewer agents

`{reviewer}` is `codex`, `claude` or a custom reviewer's name; 404 for a custom reviewer that does not review the repository.

- `POST …/pulls/{n}/reviewers/{reviewer}`: review now, whatever the limit. Answers 202 with `run_id`.
- `GET …/pulls/{n}/reviewers/{reviewer}`: its runs (with `usage`, what each cost) and this pull request's settings.
- `PATCH …/pulls/{n}/reviewers/{reviewer}`: this pull request's `enabled` and `max_iterations`; null follows the settings.
- `GET …/reviewers`: the reviewer agents that review the repository: `login`, `reviewer` (as `{reviewer}` above), `engine`, `reviews` (`code` or `description`), `automatic` (whether it reviews the caller's pull requests on its own) and `max_iterations`, never their instructions. `POST …/pulls` answers with those of the new pull request, for it, in `reviewer_agents`.
- `GET|POST /api/settings/reviewers`, `GET|PATCH|DELETE /api/settings/reviewers/{name}`: custom reviewers, with their file's keys plus `path`, `login` and the `error` that keeps one from running. PATCH changes the fields given and refuses `name`.

## git

A repository galley keeps a clone of (`POST /api/repos {github}`) has `git_url`, `/git/{owner}/{name}.git`, which git pushes branches to and fetches from over git's smart HTTP, protocol v2 included. Other paths under it, git's dumb protocol, unknown repositories and those registered by path get 404, and the hosts above apply. A push:

- moves branches only: `refs/heads/…`. The rest are galley's: `refs/remotes/origin/…`, which it fetches from GitHub (the default branch, base branches, and a published branch after GitHub refused a push), and its pins, which it does not advertise.
- deletes no branch.
- replaces a branch only by a fast-forward, or with a lease on the commit galley has there: the push option `lease=<branch>:<sha>`, an empty `<sha>` for a branch galley does not have, as in `git push --force-with-lease=<branch>:<sha> -o lease=<branch>:<sha> <git_url> <branch>` (git checks `--force-with-lease` on the pushing side only).

What it refuses comes back as `remote: galley: <branch>: <why>`. A push answers once galley has synced the repository's open pull requests with it, so a call right after it sees the new head. Publishing pushes from the clone to GitHub over https with `gh`'s credentials.

## gh shapes

- `GET …/gh/pulls[/{n}]?fields=<a,b>`: what `gh pr list|view --json` prints. Besides gh's fields: `reviewThreads`, `publishedUrl`, `waiting`, `isPinned`, `autoPublishRequest`, `reviewRequests` (with `status`, `commit`, `startedAt`), `turn`, `unpublishedChanges`, `baseConflicts`, `githubStatus`, `client` (`X-Galley-Client` when it was staged; null without), `ref` (`s4` for staged pull request s#4, as the CLI takes it), and `byReviewerAgent` on each review (such an approval is not in `reviewDecision`). `state` is also `STAGED` and `PUBLISHED`.

## Other

- `GET /api/settings`, `PUT /api/settings/{codex|claude}`, `PUT /api/settings/publish` (`mergeMethod`, `signingRetries`: 0 to 5).
- `POST /api/repos` `{path}`: register the repository at that path. Its `full_name` is the GitHub owner/name of its remote, and follows the remote when it names another (a repository renamed on GitHub); the old name still works under `/api/repos`, and its pages redirect.
- `POST /api/repos` `{github}`, on a server with `GALLEY_CLONES`: register a GitHub repository by its owner/name, in any case. One registered already as that GitHub repository is answered, also one registered by path, which stays so. Otherwise galley clones it into its data directory, with the default branch fetched from GitHub (502 when GitHub does not answer with one), and the repository's `git_url` is where branches go in (see [git](#git)). Registering one twice at once clones it once. Without `GALLEY_CLONES`, `path` is required.
- `POST /api/markdown`: also takes `pull` (a pull request's API path), to link references as its pages do, `s#4` to staged pull request 4 among them.
- `POST /api/uploads`: an image's bytes; answers with its `path`, `/uploads/<sha256>.<ext>`, served by `GET /uploads/<sha256>.<ext>`.
- `GET /api/meta`: `{"name": "galley", "version": …, "features": […]}`, so the CLI knows it reached galley and not another program on its port. While the server starts, the same with 503. `features` names what the server can do that an older one could not, so a newer CLI can ask for the server to be updated; none yet. Once started, `url` is its public URL, which the CLI's own links (`galley browse`, `--web`) start with, and `desktop_app` is `{"connected": …, "open_links": …}`: whether the desktop app on the caller's computer follows the server's live updates, and whether it opens galley links, so that `galley browse` and `--web` open them in it. A request through a proxy on the server's computer, such as `tailscale serve`, is from the computer whose address the proxy puts last in `X-Forwarded-For`; through a proxy that leaves the header out, every request is the server's computer's.
- `GET /api/health`, and `GET /events` (server-sent events). The desktop app's stream adds `?desktop=1`, and `&open_links=1` while it opens galley links: its menu's Open galley links in the app is on, and `galley://` links go to it. Pages opened in a browser on its computer then hand off to it.
- `contents` defaults `ref` to `HEAD`, not the default branch.
